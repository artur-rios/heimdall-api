## Phase 1 — Upgrade the library and refactor the actor

The solution does not compile between 1.1 and 1.8. Nothing here changes behaviour.

1.1 Bump `ArturRios.Util.WebApi` to `3.0.0` in
`src/Presentation/ArturRios.IdentityManager.WebApi/ArturRios.IdentityManager.WebApi.csproj`;
`dotnet restore`. Confirm `ArturRios.Util.Test` 2.2.0 (which pins 2.1.0) still resolves and that its
`WebApiTest<T>.Authorize` path does not touch a removed type.

1.2 Add `WebApi/Security/IdentityUser.cs` — `sealed record IdentityUser(Guid Id, int RoleId, Guid? ScopeId, IReadOnlyCollection<Guid> OwnedScopeIds) : IAuthenticatedUser`.

1.3 Add `WebApi/Security/IdentityUserMapper.cs` — `IAuthenticatedUserMapper`. `ToClaims` writes
`id`, `roleId`, and `scopeId`/`ownedScopeIds` per role; `FromClaims` parses them back with `TryParse`
and returns `null` on anything it cannot interpret, per the interface contract.

1.4 `Startup.ConfigureSecurity`: `AddTokenAuthentication<IdentityUserMapper>(...)`, options unchanged.

1.5 `Shared/Security/IActorScoped.cs`: `long ActingPersonId` → `Guid`, doc comment updated to say
public identifier.

1.6 Same type change on the eight inputs: `CreateUserCommand`, `CreateScopeOwnerCommand`,
`UpdatePersonCommand`, `DeletePersonCommand`, `HardDeletePersonCommand`, `GetPersonByIdQuery`,
`ListScopePersonsQuery`, `ListScopeOwnersQuery`.

1.7 `IScopeOwnershipChecker` + `ScopeOwnershipChecker`: parameter to `Guid`, predicate to
`person.PublicId == actingPersonId`.

1.8 Handlers: `DeletePersonCommandHandler:48`, `HardDeletePersonCommandHandler:53`,
`UpdatePersonCommandHandler:120`, `GetPersonByIdQueryHandler:93` — compare against `person.PublicId`.
In `GetPersonByIdQueryHandler`, add `PublicId` to `PersonProjection` and key the owned-scope query on
`PublicId` (line 104).

1.9 `PersonController.ApplyActor`: `HttpContext.GetUser<IdentityUser>()`.

1.10 Repair the existing tests so the solution builds: `TestTokens` (mint through
`IdentityUserMapper`, keyed by `PublicId`), the `It.IsAny<long>()` setups on
`ActorMayManageScopeAsync`, and every `ActingPersonId = …` literal across the nine affected test
files. Check each site individually — several pass a seeded person's internal `Id` and must become
that person's `PublicId`, and the functional tests that relied on `TestTokens` minting id `1` (the
seeded master admin) need explicit intent.

1.11 `dotnet build`, then run the full suite. **Everything must be green before Phase 2** — this is
the regression gate on the refactor, and it is much cheaper to read a failure here than after the
login flow is layered on top.

## Phase 2 — The login flow

2.1 `Command/Services/AuthTokenSubject.cs`, `AuthToken.cs`, `IAuthTokenIssuer.cs`.

2.2 `WebApi/Security/JwtAuthTokenIssuer.cs` — builds an `IdentityUser`, maps it through
`IAuthenticatedUserMapper`, signs with `JwtHandler` + the registered `JwtConfiguration`, and returns
the token with its UTC expiry.

2.3 `Command/Input/LoginCommand.cs`, `Command/Output/LoginCommandOutput.cs`.

2.4 `Command/Input/Validation/LoginCommandValidator.cs` — email present and well-formed, password
present. No minimum length (design Decision 7).

2.5 `Shared/Messages/AuthMessages.cs` + `AuthMessageMap.cs`.

2.6 `Command/Handlers/LoginCommandHandler.cs` — the six steps from the design, all failures returned
as `InvalidCredentials` errors on the `DataOutput`.

2.7 `WebApi/Controllers/AuthController.cs` — `[HttpPost("auth/login")] [AllowAnonymous]`.

2.8 `Startup.AddDependencies` — validator, handler, and `IAuthTokenIssuer`.

2.9 `dotnet build` and re-run the full suite; still green (no new tests yet).
